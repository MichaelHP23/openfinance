# OpenFinance — Origin Parity Program Design

**Date:** 2026-07-30
**Status:** Approved for planning
**Scope:** Everything [Origin Financial](https://useorigin.com/) sells, minus credit-score
monitoring (explicitly cut by the user) and minus the three pillars that require a vendor
relationship or a license. Five sequential phases, P1–P5. Each phase gets its own
implementation plan; this document is the single spec they all derive from.

---

## 0. How to read this

The user's request was "look up Origin Finance and remake what they do but even better."
Origin is a platform, not a feature, so this document:

1. Enumerates what Origin actually sells.
2. Triages each item against what this app can obtain — a read-only SimpleFIN feed plus
   whatever the user types in. Some Origin headline features are not software problems and
   are cut here with the reason recorded.
3. States what the app already does, so nothing is rebuilt.
4. Specs the remainder as five phases with hard dependencies between them.

Governing constraints, restated because they decide most of the calls below:

- Self-hosted, one household by default. FastAPI + Postgres + Redis + React 19, running.
- Money is `Decimal` in Python and `NUMERIC(19,4)` in Postgres. Never float. Never a
  `float` round-trip through JSON on a figure that gets summed.
- Every financial row scopes to `household_id`.
- The LLM is optional and off by default. It phrases and it chooses which question to ask;
  it never calculates. All arithmetic happens in Postgres or in Python `Decimal`.
- Laziest thing that works. No abstraction with one implementation, no feature flag for a
  value that never changes. Cuts are recorded, not silently dropped.

Milestone vocabulary note: the M0 spec defines a roadmap numbered M1–M12. This program is
cross-cutting and would collide with that numbering, so its phases are **P1–P5**. The
mapping to the old roadmap is given in §7.

## 2. Triage

| Pillar | Verdict | Reason |
|---|---|---|
| Aggregation | **Shipped** | SimpleFIN Bridge + CSV import |
| Net worth | **Shipped, better** | Daily balance snapshots give real history; most apps reconstruct it from current balance and lie about the past |
| Investments | **Shipped** | Holdings, trade log, securities, prices |
| Auto-categorization | **P1** | |
| Budgeting | **P2** | |
| Goals | **P3** | |
| Cash flow | **P3** | |
| AI advisor | **P4** | Exists today as a read-only digest card; becomes tool-calling |
| Tax tools | **P5** | Reporting and export only. Not filing, not advice |
| Estate planning | **P5, reduced** | Encrypted document vault, beneficiary fields, readiness checklist. Not document generation — a will generated by this app would be legally worthless and dangerous to imply otherwise |
| Credit score monitoring | **Cut** | User cut it. Also needs a bureau contract |
| CFP® access | **Cut** | Requires a licensed human. Software cannot substitute, and pretending to would be giving unlicensed financial advice |
| High-yield cash account | **Cut** | Requires being a bank or partnering with one. Cannot hold user money |

The three cut pillars are the parts of Origin that are a *business*, not a program. Nothing
in the design pretends to replace them.

## 4. What "even better" means here

Four claims, each of which must be true of the shipped result or the claim gets deleted
from the README:

1. **Auditable.** Origin's categorization and budget suggestions are a black box. Every
   derived number here traces to something the user can open: a rule row, a median over
   named months, a tool call with its arguments.
2. **Real history.** Balances are only knowable in the present. Daily snapshots already run;
   forecasts and reports build on recorded history, not on back-projection.
3. **No arithmetic by the model.** Already an architectural constraint from M0. P4 extends
   it rather than relaxing it.
4. **Exportable.** Every table the app owns leaves as CSV or JSON. No lock-in, because
   there is no vendor.

## 5. Phase designs

### P1 — Categorization engine

**Purpose:** give every transaction a category, without the user doing it by hand, and
without a black box.

**Schema**

Seed the existing `categories` table with a system taxonomy (`household_id IS NULL`):
roughly 12 groups and 50 leaves — Housing, Transport, Food & Drink, Shopping, Health,
Entertainment, Travel, Bills & Utilities, Financial, Income, Transfers, Other. The exact
list lives in the implementation plan; it is data, not design.

New table:

```
category_rules
  id, household_id (FK, indexed)
  match_type      enum: merchant_contains | merchant_exact | merchant_regex
  pattern         text
  min_amount      NUMERIC(19,4) NULL
  max_amount      NUMERIC(19,4) NULL
  account_id      UUID NULL FK accounts
  category_id     UUID FK categories
  priority        integer            -- lower wins; ties broken by created_at
  source          enum: user | suggested
  created_at, updated_at
```

A rule matches when every non-null condition holds. Matching runs against
`merchant_normalized`, falling back to `merchant_raw`.

**Service** — `services/categorization.py`

- `apply_rules(db, hid, transactions)` → categorizes in memory, returns count changed.
- `categorize_new(db, hid)` — called at the end of CSV import and of each sync.
- `backfill(db, hid, only_uncategorized: bool)` — re-runs over history. `only_uncategorized`
  defaults true so a backfill never silently overwrites hand-set categories.
- `uncategorized_merchants(db, hid)` → merchant + count + total, for the suggestion flow.

A transaction whose category was set by hand carries `source=user` on the rule that would
have to exist to change it; hand edits without a rule are protected by the
`only_uncategorized` default. That is the whole conflict model — no precedence lattice.

**Suggestions (optional, LLM)** — one endpoint, `POST /categories/suggest`. Sends the list
of uncategorized merchant names (names only, no amounts, no dates, no account) and the
category taxonomy, and gets back proposed `merchant → category` pairs. They are returned to
the UI as **unsaved** proposals. The user ticks the ones they want; ticking writes
`category_rules` rows with `source=suggested`. Nothing is written by the model's say-so.
Unavailable without an API key, like every other LLM path.

**API**

```
GET    /categories                       tree, system + household
POST   /categories                       create custom
PATCH  /categories/{id}
DELETE /categories/{id}                  household rows only; system rows are immutable
GET    /category-rules
POST   /category-rules
PATCH  /category-rules/{id}
DELETE /category-rules/{id}
POST   /category-rules/reorder           priority reshuffle
POST   /categorization/backfill          {only_uncategorized: bool} → {changed: n}
GET    /categorization/uncategorized     merchant rollup
POST   /categories/suggest               LLM, returns proposals, writes nothing
```

**UI**

- Transactions page: a category column, inline edit. On change, a quiet prompt —
  "Always categorize *Whole Foods* as Groceries?" — that creates the rule.
- New Rules page: ordered list, drag to reprioritize, a "test against my history" button
  that shows the match count before saving.
- Uncategorized panel with the suggest flow.

**Tests** — rule precedence, amount-band matching, regex safety (reject patterns that fail
to compile; cap pattern length), backfill respecting hand edits, import and sync both
categorizing, system categories not deletable, suggestions writing nothing until confirmed.

**Cut:** ML categorization, per-transaction split across categories, tags. Splits are
plausible later; nothing in this schema blocks them.

### P2 — Budgets

**Depends on:** P1.

**Schema**

```
budgets
  id, household_id (FK, indexed)
  category_id  UUID FK categories
  month        DATE            -- always the 1st; the month is the period
  amount       NUMERIC(19,4)
  rollover     boolean default false
  created_at, updated_at
  UNIQUE (household_id, category_id, month)
```

Monthly periods only. Weekly and custom periods are cut — a period abstraction with one
implementation is exactly the thing this codebase avoids.

**Service** — `services/budgets.py`

- `status(db, hid, month)` → per category: budgeted, actual, remaining, and **pace**
  (fraction of month elapsed vs. fraction of budget spent). Pace is what makes a budget
  useful mid-month and is arithmetic, not a model call.
- `rollover_carry(db, hid, month)` → for `rollover=true` rows, unspent prior-month amount
  folds into this month's effective budget. Carry is computed on read, never written, so
  turning rollover off cannot corrupt history.
- `suggest(db, hid, month)` → trailing 3-month median actual per category, rounded to the
  nearest 5. This is Origin's "AI sets up your budget" without the AI — a median is
  explainable, reproducible, and defensible in a way a model's guess is not.
- `copy_from(db, hid, src_month, dst_month)`.

**API**

```
GET  /budgets/{month}          status for every category, budgeted or not
PUT  /budgets/{month}          upsert a set of {category_id, amount, rollover}
POST /budgets/{month}/suggest  returns medians; writes nothing
POST /budgets/{month}/copy     {from: "2026-06"}
```

**UI** — Budgets page. Per-category row: bar, budgeted, actual, remaining, pace indicator
that goes amber when spending outruns the month. Month switcher. Suggest button fills the
inputs and leaves them dirty until saved.

**Tests** — pace arithmetic at month boundaries, rollover computed on read across three
months, median suggestion ignoring months with no data, upsert idempotence, category
deleted while budgeted (budget row goes with it).

**Cut:** envelope budgeting, zero-based budgeting, per-account budgets, notifications.

### P3 — Goals and cash-flow forecast

**Depends on:** P2 (the forecast uses budgeted discretionary spend).

**Schema**

```
goals
  id, household_id (FK, indexed)
  name           text
  kind           enum: savings | debt_payoff
  target_amount  NUMERIC(19,4)
  target_date    DATE NULL
  monthly_funding NUMERIC(19,4) NULL
  status         enum: active | achieved | archived
  created_at, updated_at

goal_accounts        -- which balances count toward the goal
  goal_id, account_id
  PRIMARY KEY (goal_id, account_id)
```

Progress is the summed current balance of the linked accounts (sign-flipped for
`debt_payoff`, where progress is the debt paid down from the starting balance). No manual
"contributions" table — the balance is the truth, and a contributions ledger that can
disagree with the bank is a bug factory.

**Service** — `services/forecast.py`

`project(db, hid, months, hypotheticals=[])` → a daily series:

1. Start at today's summed cash-account balances.
2. Walk forward day by day. On each day, apply every active `RecurringSeries` whose cadence
   lands there, using `typical_amount` and `direction`.
3. Subtract non-recurring discretionary spend, spread evenly, from the current month's
   budgeted amounts for categories with no recurring series attached.
4. Apply any hypothetical outflows or inflows passed in.
5. Emit `{date, projected_balance, contributions: [...]}` — every day carries the list of
   what moved it, so any point on the chart is explainable.

Derived from that series: the first date the balance goes negative (if any), the projected
month-end balance, and the projected surplus.

`can_i_afford(db, hid, amount, on_date, months)` → runs `project` twice, with and without
the outflow, and returns both series plus a verdict: whether the balance stays above zero,
the minimum balance reached, and what it does to each active goal's date. This is the
question Origin's advisor advertises. Here it is a model with a chart, not a sentence.

`goal_projection(db, hid, goal_id)` → date the goal is reached at current funding, using the
forecast surplus when `monthly_funding` is null.

**API**

```
GET    /goals                  with progress and projected date
POST   /goals
PATCH  /goals/{id}
DELETE /goals/{id}
GET    /forecast?months=6
POST   /forecast/afford        {amount, on_date, months}
```

**UI** — Goals page with progress rings and projected dates. Forecast chart on the Overview
page with a negative-balance marker. "Can I afford…" input beneath the chart, rendering
both lines overlaid.

**Tests** — cadence walking across month ends and leap day, biweekly drift over a year,
a series whose `next_expected_on` is in the past, forecast with zero recurring series,
`can_i_afford` on an amount that empties the account, debt-payoff progress direction,
goal with no linked accounts.

**Cut:** avalanche/snowball strategy engines, Monte Carlo, retirement projection.

### P4 — AI advisor v2

**Depends on:** P1–P3 (its tools are their read services).

**What changes:** today `services/insights.py` builds a digest and makes one LLM call with
it. That becomes a tool-calling loop. The digest stays, as the opening context.

**Tools** — all read-only, all thin wrappers over services that already exist after P1–P3:

| Tool | Backed by |
|---|---|
| `net_worth_history(months)` | `services/snapshots.py` |
| `spend_by_category(start, end, group_by)` | P1 + `services/transactions.py` |
| `transaction_search(merchant, category, min_amount, max_amount, start, end, limit)` | `services/transactions.py` |
| `budget_status(month)` | P2 |
| `cashflow_forecast(months, hypothetical_amount, hypothetical_date)` | P3 |
| `goal_progress()` | P3 |
| `holdings_summary()` | `services/portfolio.py` |
| `recurring_list(status)` | `services/recurring.py` |

Constraints, enforced in code and not merely in the prompt:

- **No mutation tools.** The tool registry contains read functions only. The model cannot
  create, edit, or delete a row through any path.
- **No raw SQL tool.** Parameters are typed and validated by Pydantic; the model chooses
  arguments, never query text.
- **Every number comes from a tool result.** Same instruction the digest already carries,
  now with the tools to satisfy it.
- **Bounded loop.** Max 8 tool calls per question, max 2 minutes wall clock. Exceeding
  either returns what it has with a note, rather than looping on the user's API bill.
- **`transaction_search` returns at most 50 rows** and is the only tool that returns
  individual transactions. Everything else returns aggregates.

**API**

```
POST /insights/ask   {question} → {answer, trace: [{tool, args, result_summary}], model}
GET  /insights/digest  (unchanged)
GET  /insights/available (unchanged)
```

**UI** — the Overview assistant card becomes a conversation. Under each answer, a
collapsible trace listing each tool call with its arguments and what came back. That trace
is the differentiator: Origin gives you a confident sentence, this gives you the sentence
and the receipt.

**Privacy** — the README already says enabling the assistant sends a summary of finances to
Anthropic's API. P4 widens what can be sent: aggregates the model asks for, and up to 50
individual transactions per search. The README section gets updated to say exactly that,
in those terms. Off by default, unchanged.

**Tests** — tool schemas validate and reject out-of-range args, the loop terminates at the
cap, a tool raising does not kill the turn, no mutation function is reachable from the
registry (assert the registry against an allowlist), trace matches the calls made,
everything degrades to 503 with no API key.

**Cut:** conversation memory across sessions, streaming, multi-turn follow-up state beyond
the current request, model-initiated actions.

### P5 — Reports, tax, and the document vault

**Depends on:** P1 (reports are category-shaped). Otherwise independent.

**Reports** — no new tables. Aggregation endpoints plus a page.

```
GET /reports/spending?start&end&group_by=category|merchant|month
GET /reports/income-vs-expense?months=12
GET /reports/year-in-review?year=2026
```

Year-in-review: total in, total out, savings rate, biggest category, biggest single
transaction, new subscriptions started, subscriptions cancelled, net worth delta.

**Tax** — reporting only. The word "advice" appears nowhere in the UI.

```
GET /tax/realized-gains?year=2026     FIFO lots from the existing trade log
GET /tax/income-summary?year=2026     dividends + interest from categorized transactions
GET /tax/export?year=2026             Schedule-D-shaped CSV
```

FIFO lot matching runs over `models/trade.py`, which already records the buys and sells.
Wash-sale detection is **cut** — getting it wrong is worse than not having it, and the
correct implementation needs substantially identical-security logic this app cannot do.
The export says so on its face.

**Vault**

```
documents
  id, household_id (FK, indexed)
  kind          enum: will | trust | insurance | deed | title | statement | other
  title         text
  filename      text
  content_type  text
  size_bytes    integer
  ciphertext_path text          -- on disk, under a data volume
  nonce, wrapped_key  bytea     -- same envelope scheme as provider credentials
  notes         text NULL
  created_at, updated_at
```

Files are encrypted at rest with the AES-GCM envelope already implemented for provider
credentials, bound to the household. Bytes are written encrypted and only ever decrypted in
the response stream for a download.

`accounts.beneficiary` — a nullable text column. Not a model, not a table. One string per
account is what a beneficiary record actually is until there is a reason for more.

Estate readiness checklist: a computed list, no storage. Do you have a will on file? A
beneficiary on every retirement and insurance account? A deed for each property account? It
reports gaps; it does not generate documents.

**Export**

```
GET /export/all.zip    every table the household owns, one CSV per table
```

**Tests** — FIFO across partial sells and multiple lots, realized gains for a year with no
sells, upload/download round-trip byte-identical, ciphertext on disk is not the plaintext,
a document from another household is not reachable, checklist gap detection, export
containing every table (assert against the model registry so a new model fails the test).

**Cut:** PDF report rendering, document generation, OCR, wash sales, cost-basis methods
other than FIFO, e-signature.

## 6. Cross-cutting

**Migrations** — one Alembic revision per phase, in `backend/migrations/versions`. P1 seeds
system categories in the migration itself; seed data that the app requires to function is
schema, not fixtures.

**Testing** — the repo's existing shape: pytest against a real Postgres container per
service, vitest for components, one Playwright flow per phase. TDD, per the repo habit.

**Performance** — `spend_by_category` over a decade of transactions is the only query with
real growth. Index `transactions (household_id, category_id, posted_at)` in P1's migration.

**Nothing new in the dependency tree.** Every phase uses FastAPI, SQLAlchemy, Pydantic,
React Query, and Recharts, all already installed.

## 7. Sequencing and roadmap mapping

Strictly sequential; each phase's tests must pass before the next begins.

| Phase | Old roadmap slot | Blocks |
|---|---|---|
| P1 Categorization | M1 (rules engine, categorization) | P2, P4, P5 reports |
| P2 Budgets | M3 | P3, P4 |
| P3 Goals + forecast | M4 + M7 | P4 |
| P4 AI advisor v2 | M6 | — |
| P5 Reports, tax, vault | M8 | — |

M2 (Plaid) is superseded by the shipped SimpleFIN provider. M9 (recurring detection) is
shipped. M10–M12 are untouched by this program.

## 8. Non-goals

Credit-score monitoring, CFP access, a cash account, wash-sale detection, document
generation, tax filing, investment advice, moving money, mobile apps. The first three are
Origin's business model rather than its software; the rest are either legally fraught or
worse-than-nothing when approximated.
